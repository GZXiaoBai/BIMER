# EmotionTalk 双 GPU 分模态特征提取设计

## 1. 背景

当前 EmotionTalk 特征提取按分片串行执行文本、音频和视觉三个阶段。文本、XLS-R 和 R3D-18 均运行在 `cuda:0`，音视频解码及 YuNet 人脸检测也位于主进程中。该实现能够正确产出特征，但会造成以下性能问题：

- GPU 计算经常等待 FFmpeg、OpenCV 和 YuNet 的 CPU 工作；
- 第二张 Kaggle T4 未被使用；
- R3D-18 以单视频方式推理，无法充分利用 GPU 批处理；
- 三种模态绑定在同一分片任务中，任何阶段失败都会阻止整个分片完成；
- 无法独立观察各模态吞吐量、失败样本和恢复进度。

本设计在不改变最终 `FeatureShard` 格式和后续训练接口的前提下，将提取流程改为独立、可恢复的分模态流水线。

## 2. 目标与非目标

### 2.1 目标

- GPU 0 承担文本与语音编码，GPU 1 承担视觉编码；
- 使用 CPU 工作进程并行完成音频解码、视频采样和人脸检测；
- 三种模态独立缓存、独立恢复，并按 `sample_id` 严格合并；
- 复用经过校验的旧版完整分片；
- 保持最终特征维度、掩码语义、样本顺序和训练接口不变；
- EmotionTalk validation 全量提取尽量控制在 60 分钟内；
- 优化版失败时可以回退到现有串行命令。

### 2.2 非目标

- 本次不修改 XLM-R、XLS-R、YuNet 或 R3D-18 模型结构；
- 不改变数据集官方划分、标签或样本定义；
- 不在本次优化中训练融合模型；
- 不用零向量伪装损坏且本应有效的音视频输入；
- 不删除旧流程或已有有效产物。

## 3. 方案选择

采用“分模态双 GPU 流水线”方案：

```text
manifest
  ├─ text batches ─────────────────── GPU 0 ── text staging shards
  ├─ audio CPU decode workers ─ queue ─ GPU 0 ── audio staging shards
  └─ video sampling + YuNet workers ─── GPU 1 ── vision staging shards
                                                      │
                                 validate and join by sample_id
                                                      │
                                      final FeatureShard files
```

没有采用“两张 GPU 各处理一半完整样本”，因为该方案会在每张卡重复加载全部模型，并加剧 CPU 解码竞争。没有采用“单 GPU 生产者—消费者”，因为它仍会闲置第二张 T4。

## 4. 组件与职责

### 4.1 样本规划器

样本规划器读取 manifest，保留 manifest 中的确定性顺序，并生成当前数据集及划分的 `sample_id` 列表。启动时它执行以下检查：

1. 拒绝重复 `sample_id`；
2. 检查已有最终分片，只有样本 ID、顺序、维度、掩码和数值均合法时才标记为完成；
3. 从三个 staging 目录读取独立模态进度；
4. 只把尚未完成的样本派发给对应模态流水线。

已有旧版最终分片是权威完成结果，不需要重新提取其中任何模态。

### 4.2 文本流水线

- 运行设备：GPU 0；
- 初始批量：64；
- 输入：原始文本；
- 输出：768 维文本特征及有效掩码；
- 遇到 CUDA OOM 时将批量减半并重试，最低为 1；
- 文本为空时按照既有数据契约处理，不静默制造有效文本特征。

文本阶段完成后释放可释放的临时张量和缓存，再在 GPU 0 上运行语音编码，避免两个大型编码器同时争用显存。视觉流水线可同时在 GPU 1 运行。

### 4.3 音频流水线

- CPU 解码工作进程默认数：4，可由命令行配置；
- 使用有界队列提供背压，防止已解码波形耗尽内存；
- 解码格式：16 kHz、单声道 float32；
- 运行设备：GPU 0；
- 初始 GPU 批量：8；
- 输出：1024 维语音特征及有效掩码。

工作进程只返回可序列化的轻量结果：`sample_id`、波形、采样率和错误信息。Transformers 模型只存在于 GPU 消费进程中。

### 4.4 视觉流水线

- CPU 工作进程默认数：4，可由命令行配置；
- 每句均匀采样 16 帧；
- 在 CPU 工作进程中执行视频读取、YuNet 检测、主脸选择和裁剪；
- 累计最多 8 个有效 clip 后送入 GPU 1 的 R3D-18；
- 输出：512 维视觉特征及有效掩码。

每个 clip 保留固定的帧数和尺寸，以便堆叠成批。少于 4 帧检测到人脸时，按项目数据约定将视觉模态标记为缺失，视觉特征填零且 `vision_mask=False`。该情况是正常的缺失模态，不计为流水线错误。

### 4.5 模态分片存储

staging 目录采用以下结构：

```text
<output>/staging/<dataset>/<split>/
  text/features-00000.npz
  audio/features-00000.npz
  vision/features-00000.npz
  errors.jsonl
  run-metadata.json
```

每个模态分片至少包含：

- `sample_ids`：字符串数组；
- 对应模态的二维特征数组；
- 对应模态的布尔有效掩码；
- schema 版本、模型标识及必要的提取参数。

分片先写入同目录临时文件，完成维度、ID、NaN/Inf 和元数据校验后再原子重命名。临时文件不视为有效进度。

### 4.6 合并器

合并器按 manifest 中的 `sample_id` 和顺序连接三种模态，而不是依赖各流水线的完成顺序。合并前必须检查：

- 三种模态均覆盖所有待合并 ID；
- ID 唯一且集合完全一致；
- 特征维度分别为 768、1024、512；
- 特征中不存在 NaN 或 Inf；
- 掩码长度与样本数相同；
- 已有最终分片与新分片没有重复覆盖。

任何检查失败都会停止合并并报告差异。最终仍通过现有 `FeatureStore` 写出训练代码可直接读取的 `FeatureShard`。

## 5. 并发与资源管理

- GPU 0 上的文本和语音阶段顺序执行；GPU 1 的视觉阶段与两者并行；
- CPU 音频与视觉工作池相互独立，工作进程数量可分别调整；
- 队列必须有容量上限，并在消费者失败时通知生产者退出；
- 主进程持续检查子进程状态，任何非预期退出都会终止对应流水线；
- 每次 GPU 推理使用 `torch.inference_mode()` 和适合 T4 的混合精度；
- OOM 仅对当前批次执行批量减半重试，不重复已成功写入的分片；
- 进度日志至少报告已完成样本数、吞吐量、队列深度、当前批量和预计剩余时间。

## 6. 错误语义

### 6.1 可接受的缺失模态

- 按规则检测不到足够人脸：零视觉特征，`vision_mask=False`；
- 数据本身确实没有可用音频：零语音特征，`audio_mask=False`，同时保留原因。

### 6.2 不可静默忽略的错误

- 文件不存在、无法解码、模型推理失败；
- 本应有音频但 FFmpeg 解码失败；
- 工作进程崩溃、队列失联或 staging 文件损坏；
- 样本 ID、维度或数值校验失败。

错误记录包含模态、`sample_id`、文件路径、错误类型和摘要。若错误使样本无法满足数据契约，命令以非零状态退出且不得生成对应最终分片。

## 7. CLI 与兼容性

保留当前串行提取入口作为回退路径。新增或扩展提取命令以支持：

- 选择 `serial` 或 `parallel` 执行模式；
- 指定文本/语音设备和视觉设备；
- 配置音频、视觉 CPU 工作进程数；
- 配置三种模态的初始批量和队列容量；
- 仅运行指定模态、仅合并、强制重新校验；
- 输出机器可读的运行元数据和错误报告。

默认值针对 Kaggle T4 x2 设置，但在单 GPU 或 CPU 环境中应能通过显式配置退化运行。

## 8. 测试策略

### 8.1 单元测试

- 模态分片读写、schema 和原子提交；
- 按 ID 合并与 manifest 顺序恢复；
- 重复、缺失、额外或乱序 ID 的拒绝行为；
- NaN/Inf、错误维度和损坏文件检测；
- 已有最终分片的安全复用；
- OOM 批量退避逻辑；
- 缺失任意一种或两种模态时不产生 NaN；
- 子进程异常能传回主进程，不发生无限等待。

### 8.2 集成测试

- 使用模拟编码器验证 CPU 队列、GPU 批处理、背压和断点续跑；
- 使用 16 个真实样本对比新旧实现；
- 特征比较容差为 `rtol=1e-4`、`atol=1e-5`；
- 最终样本 ID、顺序、维度和掩码必须完全一致。

### 8.3 Kaggle 验证

1. 先处理 32 个样本，确认 GPU 0 和 GPU 1 均有明显负载；
2. 记录模型加载时间、各模态吞吐量、峰值显存和总耗时；
3. 中途终止并恢复一次，验证 staging 断点续跑；
4. 完整运行 validation；
5. 与旧任务产物比较样本数、ID、特征维度、掩码和固定子集数值。

## 9. 验收标准

- 本地全部测试通过；
- 16 个真实样本的新旧特征在规定容差内一致；
- 任意一种或两种模态缺失时不崩溃且不产生 NaN；
- staging 中断后可以继续，已完成分片不重复计算；
- 双 T4 运行时两张 GPU 均承担预期工作；
- validation 全量耗时目标不超过 60 分钟；若受 Kaggle I/O 或 CPU 配额影响未达到，必须提供分阶段耗时和瓶颈证据；
- 最终特征能够被现有训练入口直接读取；
- 优化版完全验证前，旧串行路径和已有产物保持可用。

## 10. 切换与回退

优化代码先在本地模拟数据和真实小样本上通过测试，再上传 Kaggle。当前串行任务继续运行。优化版完成 32 样本试跑和新旧一致性验证后，再用于尚未处理的 validation、train 和 test 数据。

若优化版出现不可接受的特征差异、死锁、频繁 OOM 或产物校验错误，立即切回串行模式。staging 产物与最终特征目录隔离，因此回退不需要删除旧结果。
